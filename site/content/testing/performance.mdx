## The benchmarks

The command `pnpm bench` starts each case in a separate Node.js process. Each process measures each benchmark with tinybench. A value is the mean time of one operation of the benchmark. The command does 5 rounds, with a different order of the cases in each round, and a value is the median of the rounds. The rounds decrease the effect of other work on the machine.

| Benchmark | What it does |
| --- | --- |
| await loop | One async function with 10,000 `await` steps. |
| async calls | 10,000 async functions in sequence, each with one `await`. |
| then chain | A chain of 10,000 `then` callbacks. |
| concurrent tasks | 1,000 async functions at the same time, each with 10 `await` steps, in one context. |
| request handlers | 1,000 request handlers, each in its own context, with three `await` steps and one read of the context. |
| get in nested contexts | 100,000 reads with `get()`, 5 contexts deep. |

## The cases

| Case | What it measures |
| --- | --- |
| Plain JavaScript | The same code without the library. A `Variable` class without propagation gives the same API. |
| Transform only | The Babel preset with a plain coroutine. This case shows the cost of the transform without the cost of the context. |
| Library | The Babel preset and the browser runtime. |

## What the results tell

- **The transform.** Each async function of transformed code is a generator that the coroutine operates. This costs more than a native async function. The number of microtask steps of each `await` does not change.
- **The context.** Each `then` callback and each step of the coroutine sets the context and sets it again after the step. Each `then` call makes two small wrappers.
- **`get()`.** One read takes approximately 4 ns. The plain case reads one field, so the factor is large, but the time is small.

<Callout type="note">
  The values are microbenchmarks. The benchmarks do no other work, so the factors are the largest possible factors. Measure your own application before and after you add the library.
</Callout>

## Size

The command `pnpm bench:size` builds minified bundles with Vite 8.3.4, and measures them with gzip and brotli. Vite builds each bundle as an application, because a library build of Vite keeps the white space. The bundle of the runtime keeps all exports of `async-browser-context` and `async-browser-context/runtime`. The results go to `bench/results/size.json`.

| Code | Minified | gzip | brotli |
| --- | --- | --- | --- |
| The runtime: the classes, the patches and the runtime of the transform | 17.5 kB | 6.0 kB | 5.4 kB |
| zone.js 0.16.3, for comparison | 34.7 kB | 11.8 kB | 10.7 kB |

The transform also makes the code of the application larger. The command builds each package of a set of npm packages four times. Each bundle keeps all exports of the package, and does not contain the runtime. The values are gzip sizes.

- **User interface code.** React DOM has no async functions, so the transform does not change it. In an application, the code with async functions is usually a small part.
- **Code with much async code.** The transform adds 3 to 6.4 percent to API clients. Each async function becomes a generator in a function that starts `coroutine`.
- **Small packages with `for await`.** Babel adds its helper for `for await` to each module that has such a loop: approximately 0.5 kB with gzip. This is the cause of the large percent of TanStack Query. Since version 0.2.3, the async generators use the driver of the runtime, so the modules do not contain the async generator helper of Babel.
- **The names.** The preset gives the name of each async function to the callback hooks. The option `names: false` removes the names: 0.1 to 1.8 percent of the package.
- **The target ES2016.** A compiler with this target also keeps the context through `await`, except rule C5 ([build tools](/docs/guides/build-tools)). The target also changes newer syntax, so the bundles are larger than with the preset.

## Browsers

The command `pnpm bench:browsers` measures `await` and `then` in Chromium, Firefox and WebKit with Playwright. One run repeats a workload until at least 100 ms have passed, and divides the time by the number of repetitions. Each value is the time of 50,000 steps in ms, as the median of 7 runs. Each case has its own page, and the order of the cases changes in each run. "Babel helper" is the async transform of Babel with its own helper, without the library. Many compiled packages use such a helper.

- **Async generators.** Since version 0.2.3, the driver of the runtime operates each async generator with a native `await`. Before, the helper of Babel was in each module, and each step was a `then` callback. With version 0.2.2, the async generator workload took 11.2 ms in Chromium, 560 ms in Firefox and 16 ms in WebKit.
- **The coroutine.** Since version 0.2.2, the coroutine operates each async function with a native `await`. Before, each step was a `then` callback, as in the Babel helper. In Firefox, 50,000 awaits of `null` took 292 ms with version 0.2.1.
- **Firefox and the patch of `then`.** Firefox has a fast path for `await` of a promise. A patch of `Promise.prototype.then` stops this fast path, also for code without the transform. Each `await` of a promise then takes approximately 0.8 µs more. {/* TODO(bench) */} zone.js also patches the promises, so it has the same cost.
- **Playwright and Firefox.** Playwright controls Firefox with the debugger API. Firefox then records an async stack for each `then` callback. Thus, `then` callbacks take more time in this measurement than in a Firefox without Playwright. With the preference `javascript.options.asyncstack` set to `false`, a chain of steps in `then` callbacks was 7 times faster. {/* TODO(bench) */}
