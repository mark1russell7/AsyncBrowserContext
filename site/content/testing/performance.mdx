## The benchmarks

The command `pnpm bench` starts each case in a separate Node.js process. Each process measures each benchmark with tinybench. A value is the mean time of one operation of the benchmark. The command does 5 rounds, with a different order of the cases in each round, and a value is the median of the rounds. The rounds decrease the effect of other work on the machine.

| Benchmark | What it does |
| --- | --- |
| await loop | One async function with 10,000 `await` steps. |
| async calls | 10,000 async functions in sequence, each with one `await`. |
| then chain | A chain of 10,000 `then` callbacks. |
| concurrent tasks | 1,000 async functions at the same time, each with 10 `await` steps, in one context. |
| request handlers | 1,000 request handlers, each in its own context, with three `await` steps and one read of the context. |
| get in nested contexts | 100,000 reads with `get()`, 5 contexts deep. |

## The cases

| Case | What it measures |
| --- | --- |
| Plain JavaScript | The same code without the library. A `Variable` class without propagation gives the same API. |
| Transform only | The Babel preset with a plain coroutine. This case shows the cost of the transform without the cost of the context. |
| Library | The Babel preset and the browser runtime. |

## What the results tell

- **The transform.** Each async function of transformed code is a generator that the coroutine operates. This costs more than a native async function. The number of microtask steps of each `await` does not change.
- **The context.** Each `then` callback and each step of the coroutine sets the context and sets it again after the step. Each `then` call makes two small wrappers.
- **`get()`.** One read takes approximately 4 ns. The plain case reads one field, so the factor is large, but the time is small.

<Callout type="note">
  The values are microbenchmarks. The benchmarks do no other work, so the factors are the largest possible factors. Measure your own application before and after you add the library.
</Callout>

## Size

The command `pnpm bench:size` builds minified bundles with Vite 8.3.4, and measures them with gzip. The results go to `bench/results/size.json`.

| Code | Minified | gzip | brotli |
| --- | --- | --- | --- |
| The runtime: the classes, the patches and the runtime of the transform | 19.0 kB | 5.9 kB | 5.1 kB |
| zone.js 0.16.3, for comparison | 45.6 kB | 13.3 kB | 11.9 kB |

The transform also makes the code of the application larger. The command builds each package of a set of npm packages four times. Each bundle keeps all exports of the package, and does not contain the runtime. The values are gzip sizes.

| Package | Async functions | Without the transform | With the Vite plugin | With `names: false` | Target ES2016, no plugin |
| --- | --- | --- | --- | --- | --- |

| @tanstack/query-core 5.104.2 | 8 | 13.1 kB | 13.8 kB (+5.9%) | 13.8 kB (+5.8%) | 16.9 kB (+29.3%) |
| ky 2.2.0 | 28 | 12.1 kB | 12.6 kB (+4.3%) | 12.5 kB (+3.3%) | 14.3 kB (+17.9%) |
| idb 8.0.4 | 2 | 1.8 kB | 2.3 kB (+31.9%) | 2.3 kB (+31.4%) | 3.0 kB (+71.9%) |
| @supabase/supabase-js 2.117.3 | 358 | 62.6 kB | 66.1 kB (+5.5%) | 65.1 kB (+3.9%) | 67.3 kB (+7.5%) |
| openai 7.32.0 | 145 | 91.7 kB | 100.1 kB (+9.1%) | 99.4 kB (+8.4%) | 100.9 kB (+10%) |
| @aws-sdk/client-s3 3.1149.0 | 210 | 100.8 kB | 105.7 kB (+4.9%) | 105.2 kB (+4.4%) | 108.1 kB (+7.3%) |
| An application: React DOM, TanStack Query, supabase-js and ky | 394 | 161.9 kB | 166.5 kB (+2.9%) | 165.3 kB (+2.1%) | 171.2 kB (+5.8%) |

- **User interface code.** React DOM has no async functions, so the transform does not change it. In an application, the code with async functions is usually a small part.
- **Code with much async code.** The transform adds 4 to 9 percent to API clients. Each async function becomes a generator in a function that starts `coroutine`.
- **Small packages with `for await` or async generators.** Babel adds its helpers for async iteration to each module that has such code: approximately 0.5 kB with gzip. This is the cause of the large percent of idb and TanStack Query.
- **The names.** The preset gives the name of each async function to the callback hooks. The option `names: false` removes the names: 0.1 to 1.6 percent of the package.
- **The target ES2016.** A compiler with this target also keeps the context through `await`, except rule C5 ([build tools](/docs/guides/build-tools)). The target also changes newer syntax, so the bundles are larger than with the preset.

## Browsers

The command `pnpm bench:browsers` measures `await` and `then` in Chromium, Firefox and WebKit with Playwright. Each value is the median time of 50,000 steps, in ms. "Babel helper" is the async transform of Babel with its own helper, without the library. Many compiled packages use such a helper.

| Browser | Workload | Native | Babel helper | Library |
| --- | --- | --- | --- | --- |
| Chromium 156 | `await null` | 2.3 | 4.0 | 4.1 |
| Chromium 156 | `await` of a promise | 5.9 | 7.3 | 5.7 |
| Chromium 156 | `then` chain | 1.8 | 1.9 | 5.2 |
| Firefox 157 | `await null` | 1.0 | 271 | 4.0 |
| Firefox 157 | `await` of a promise | 1.0 | 193 | 51 |
| Firefox 157 | `then` chain | 81 | 82 | 147 |
| WebKit 27.2 | `await null` | 3.0 | 4.0 | 5.0 |
| WebKit 27.2 | `await` of a promise | 3.0 | 4.0 | 6.0 |
| WebKit 27.2 | `then` chain | 3.0 | 3.0 | 4.0 |

- **The coroutine.** Since version 0.2.2, the coroutine operates each async function with a native `await`. Before, each step was a `then` callback, as in the Babel helper. In Firefox, 50,000 awaits of `null` took 292 ms with version 0.2.1.
- **Firefox and the patch of `then`.** Firefox has a fast path for `await` of a promise. A patch of `Promise.prototype.then` stops this fast path, also for code without the transform. Each `await` of a promise then takes approximately 0.8 µs more. zone.js also patches the promises, so it has the same cost.
- **Playwright and Firefox.** Playwright controls Firefox with the debugger API. Firefox then records an async stack for each `then` callback. Thus, `then` callbacks take more time in this measurement than in a Firefox without Playwright. With the preference `javascript.options.asyncstack` set to `false`, a chain of steps in `then` callbacks was 7 times faster.
